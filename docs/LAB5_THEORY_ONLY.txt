ТЕОРЕТИЧЕСКИЕ ВОПРОСЫ К ЛАБОРАТОРНОЙ 5

1. Bulk-операции

Bulk-операция — это операция, которая обрабатывает сразу несколько объектов за один запрос. Обычно это POST или PUT, принимающий массив JSON-объектов. Основная цель bulk-операций — уменьшить количество сетевых вызовов, упростить массовую обработку данных и обеспечить единые правила валидации и сохранения.

Преимущества bulk-операций:
- меньше HTTP-запросов;
- удобнее массовое создание или обновление данных;
- можно обеспечить общую транзакционность для всей группы объектов.

Недостатки:
- сложнее обработка ошибок;
- нужно отдельно продумать поведение при частичном сбое;
- важна корректная валидация каждого элемента списка.


2. Stream API и лямбды

Stream API — это механизм обработки коллекций в функциональном стиле. Он позволяет выполнять фильтрацию, преобразование, сортировку и агрегацию данных более кратко и выразительно.

Лямбда-выражение — это короткая форма записи функции. Лямбды часто используются внутри Stream API.

Примеры типичных операций Stream API:
- map — преобразует каждый элемент в другой;
- filter — оставляет только подходящие элементы;
- toList — собирает результат в список.

Преимущества:
- код короче и понятнее;
- легче описывать цепочки преобразований;
- удобно работать с коллекциями без ручных циклов.

Для чего нужен map:
- преобразует один тип данных в другой;
- например, Entity -> DTO;
- или Request -> результат сохранения.


3. Optional

Optional — это контейнер, который явно показывает, что значение может присутствовать или отсутствовать. Он используется вместо прямой работы с null.

Зачем нужен Optional:
- делает отсутствие значения явным;
- снижает риск NullPointerException;
- заставляет явно обрабатывать ситуацию, когда объект не найден.

Часто используемые методы:
- ofNullable — создает Optional из значения, которое может быть null;
- map — преобразует значение, если оно есть;
- filter — оставляет значение только при выполнении условия;
- orElseThrow — выбрасывает исключение, если значения нет.


4. Пирамида тестирования

Пирамида тестирования — это подход, который показывает, каких тестов должно быть больше, а каких меньше.

Уровни пирамиды:
- unit-тесты — самый нижний и самый большой уровень;
- интеграционные тесты — средний уровень;
- UI/end-to-end тесты — верхний, самый маленький уровень.

Идея пирамиды:
- unit-тесты быстрые и дешевые, их должно быть больше всего;
- интеграционные тесты проверяют взаимодействие компонентов;
- end-to-end тесты дорогие и медленные, поэтому их обычно меньше.


5. TDD

TDD (Test-Driven Development) — это разработка через тесты.

Классический цикл TDD:
- Red — пишется тест, который пока падает;
- Green — пишется минимальный код, чтобы тест прошел;
- Refactor — код улучшается без изменения поведения.

Плюсы TDD:
- код лучше проектируется;
- проще избежать лишней логики;
- тесты сразу становятся частью разработки.


6. Unit-тесты и интеграционные тесты

Unit-тест проверяет один класс или один метод изолированно от остальной системы. Обычно зависимости мокируются.

Интеграционный тест проверяет совместную работу нескольких компонентов, например controller + service + repository + база данных.

Разница:
- unit-тесты быстрые и изолированные;
- интеграционные тесты ближе к реальному поведению приложения;
- unit-тесты удобны для проверки бизнес-логики;
- интеграционные тесты показывают, что приложение работает целиком.


7. JUnit

JUnit — это основная библиотека для написания тестов в Java.

Что обычно используется:
- @Test — помечает тестовый метод;
- @BeforeEach — выполняется перед каждым тестом;
- assertions — проверки ожидаемого результата.

JUnit отвечает за запуск тестов и проверку, прошли они или нет.


8. Mockito

Mockito — это библиотека для создания mock-объектов. Она используется в unit-тестах, когда нужно изолировать тестируемый класс от его зависимостей.

Что можно делать с Mockito:
- подменять реальные зависимости моками;
- задавать поведение методов через when(...).thenReturn(...);
- проверять, был ли вызван нужный метод.

Когда Mockito особенно полезен:
- при тестировании сервисов;
- когда не нужно поднимать Spring-контекст;
- когда нужно проверить только бизнес-логику, а не всю инфраструктуру.
